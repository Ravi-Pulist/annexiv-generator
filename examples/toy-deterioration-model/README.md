# toy-deterioration-model

> **Synthetic data only. No real patient data is used, stored, or referenced anywhere in
> this repository.** Every row in `data/` is produced by `data/generate.py` from a fixed
> seed. This is a **demonstration subject, not a medical device**, and it is not CE-marked,
> not clinically validated, and must never be connected to a live clinical system.

A deliberately small, deliberately mediocre deterioration early-warning classifier.
It takes a set of synthetic vital signs and laboratory values for a single inpatient
encounter and outputs a "flag for clinician review" decision.

## Why this repository exists

It is the demo subject for an EU AI Act Annex IV technical-documentation generator.
The point of the exhibit is **documentation rigour, not model quality**: the model is a
plain logistic regression on ten features, and its measured performance is reported
honestly, with confidence intervals, in `eval/report.json`.

Two Annex IV items are **knowingly absent** so that a documentation generator has
something real to flag. They are listed in [`docs/KNOWN-GAPS.md`](docs/KNOWN-GAPS.md).

## How well it works (v0.2.0)

Badly, and on purpose. Measured on the held-out test split, n = 805, positive rate 0.138,
at the operating point selected on validation. Every figure is regenerated by
`eval/evaluate.py`; none is typed in.

| Metric | Value | 95% CI (Wilson) | n |
| --- | --- | --- | --- |
| AUROC | 0.797 | — | 805 |
| Sensitivity | 0.784 | 0.698 – 0.850 | 111 |
| Specificity | 0.650 | 0.614 – 0.684 | 694 |
| PPV | 0.264 | 0.219 – 0.314 | 330 |
| NPV | 0.949 | 0.926 – 0.966 | 475 |

It catches about four deteriorations in five, flags two encounters in five, and is wrong
about three times in four when it flags. Whether that is worth deploying is a real
question with a defensible answer either way, which is precisely what makes it useful to
document — see [`docs/metric-rationale.md`](docs/metric-rationale.md).

## Layout

| Path | What it is |
| --- | --- |
| `config/training.yaml` | Seed, split ratios, cleaning bounds, hyperparameters |
| `data/generate.py` | Synthetic encounter generator (selection + cleaning + splitting) |
| `data/manifest.json` | Dataset provenance: seed, row counts, SHA-256 of every split |
| `input_schema.py` | Pydantic model of one inference input, with units and ranges |
| `train.py` | Fits the classifier, writes `models/model.joblib` |
| `eval/evaluate.py` | Held-out evaluation with self-implemented Wilson intervals |
| `eval/report.json` | Measured performance evidence |
| `docs/` | Attested documents (YAML front-matter + prose) |
| `docs/KNOWN-GAPS.md` | The two deliberate absences — plain prose, deliberately unsigned |
| `risk-log.yaml` | Machine-checkable risk register |
| `custody/register.json` | The model pinned by SHA-256 |
| `custody/ml-bom.json` | CycloneDX 1.6 ML-BOM carrying the same digest |
| `custody/pin.py` | Regenerates both custody records from the artifacts on disk |
| `tests/test_repo.py` | Repository invariants, including the deliberate absences |

## Reproducing everything from scratch

```bash
python -m pip install -r requirements.txt
python data/generate.py     # writes data/*.csv and data/manifest.json
python train.py             # writes models/model.joblib, prints its SHA-256
python eval/evaluate.py     # writes eval/report.json
python custody/pin.py       # rewrites custody/register.json and custody/ml-bom.json
python -m pytest tests -q
```

Every script runs from the repository root. The sequence is deterministic: the seed is
`20260804`, nothing in the pipeline reads the wall clock, and running it twice from an
empty `data/`, `models/` and `eval/` produces byte-identical output — verified, including
`models/model.joblib` itself. After a full rebuild `git status` is clean; if it is not,
something in the pipeline has become non-deterministic and that is a defect.

Each stage refuses to run on stale inputs rather than warning: `train.py` re-hashes every
CSV against the manifest, `eval/evaluate.py` checks the model was fitted against the
manifest on disk, and `custody/pin.py` checks the report describes the model on disk.

`eval/report.json` carries `generated_from_commit: null`. Stamping the current HEAD into a
tracked file would make every evaluation dirty the tree with the digest of the commit
before it. A build system that wants the provenance injects it:

```bash
SOURCE_COMMIT=$(git rev-parse HEAD) python eval/evaluate.py
```

The report is instead pinned to `model_sha256` and `dataset_manifest_sha256`, which are
real content digests and better provenance than a commit id.
